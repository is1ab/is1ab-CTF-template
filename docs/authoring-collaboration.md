# 出題協作：操作、角色與題面審閱

這個插件僅用於 **template / staging 出題站**。is1abCTF 是 production 比賽站，不能安裝此插件取代正式比賽介面。

目前完成的操作路徑是「成員授權 → 提案／工單 → 本人接案 → 裁判確認提案 → 建立題目草稿 → 固定題面送審 → 回報問題／退修 → 題面確認」。正式試解與發布仍在後續階段，不能將這一版當成完整比賽系統上線。

## 角色與資料範圍

一般 CTFd 註冊帳號不會自動成為工作人員。管理員在「成員與角色」啟用帳號並勾選角色；同一帳號可兼任。管理員身分沿用 CTFd，其他工作角色不會取得 CTFd 管理員權限。

| 身分 | 本階段可做的事 | 邊界 |
| --- | --- | --- |
| 平台管理員 | 授予／撤銷工作角色、處理帳號、使用管理後台 | 是可信任的最高權限管理者；工單內仍禁止確認自己參與製作的提案 |
| PM | 建立工單、指派作者／驗題人、安排截止與預估工時、查看全場提案及進度、連結既有題目 | 不可授予角色；單有 PM 角色不能編輯題目、看 flag、官解或匯出私有資料 |
| 裁判 | 查看全場提案、確認／要求補充／列為備用／不採用 | 不能確認自己目前或曾經參與製作的題目；提案確認不是產物驗收 |
| 出題人 | 新增提案、接受自己的工作、編輯／匯出自己擁有或協作的題目、回覆問題；主作者可送出題面審閱 | 共同作者必須有啟用中的出題角色；不能加入本題驗題人為共同作者；作者不能自行結案 |
| 驗題人 | 查看被指派的工單、本人接案後審閱固定題面、回報／結案／重開問題、留下此版回饋 | 不能自薦後直接取得題目權限；不能讀 flag、內部筆記與私有原始碼；目前／歷任作者不得驗本題；題面確認不構成正式通過 |
| 維運 | 保留角色供後續執行器與賽中維運使用 | 本階段尚無正式部署操作；舊版直接操作 Docker 的入口已停用 |
| 選手支援 | 保留角色供後續賽中案件流程使用 | 不因支援角色取得全場題目或私有資料 |
| 參賽者／未授權帳號 | 使用 production 比賽站 | 不能使用 staging 出題功能、題目 API 或附件入口 |

兼任權限按角色與題目關係組合，但作者利益衝突限制優先。移除作者／共同作者後仍保留製作歷史，不能藉由交接把自己變成獨立驗題人。

平台管理員本來就可透過 CTFd 管理後台讀取資料與修改原生資料；這不是能防止惡意管理員的隔離。日常 PM、出題、裁判應使用一般帳號的工作角色。正式比賽工作帳號與參賽帳號、認證及金鑰須分開部署／管理。

## 一次走完

1. 管理員先建立或確認 CTFd 帳號，到 `/is1ab/members` 授予工作角色。此處不要求 GitHub 帳號。
2. 登入後進「我的待辦」。作者可提案；PM 可直接建立含作者、驗題人、截止與工時的工單。
3. 作者、驗題人分別按「確認接案」。無法接案時填寫原因，按「退回 PM 協調」。不能替別人接案。
4. 作者補好考點與資源需求後「送出提案確認」。提案及討論不要張貼 flag 或完整官解。
5. 裁判在所有必要人員接案且沒有作者衝突後，確認「可開始製作」。需要補充、備用、不採用都要留下原因。
6. 作者按「依此工單建立題目」。系統帶入名稱、分類及難度，建立隱藏草稿並明確連回工單。重送同一工單不會再建一題。
7. 舊題由 PM 使用工單中的「連結既有題目」指定 ID，作者須相同，一題只能連一張工單。同分類／同難度的不同工單不會互相吃掉。
8. 主作者從工單或題目頁進入「送審與版本」，按「送出題面審閱」。系統保留此刻題面；重送同版不會建立重複審閱。
9. 指定且已接案的驗題人提出具體問題；作者回覆、修改草稿，再由主作者重新送審。未結問題與回覆會延續至新版，舊版只供查閱。
10. 驗題人核對新版修正，填寫原因並「確認結案」。沒有未結問題後，填寫回饋並勾選題面確認。「我的待辦」自動顯示「題面已確認，待技術驗證」，不需再手動更新另一份狀態。

出題人也可建立未連工單的草稿或匯入舊題，方便整理材料；這些操作不代表提案已確認，也不構成發布資格。

## 題面版本與退修

每次審閱只提供當時的題名、分類、分數、題敘、tags 與 hints。提示內容可展開檢查，這是題面校閱，尚不是盲測。快照不提供 flag、私有 metadata、附件內容、官解或執行環境。

草稿、私有 flag／metadata、作者／協作者或工單版本改變後，舊審閱不再適用；作者需要重新送審。系統也會比對資料指紋，偵測管理後台直接修改題目造成的差異。角色撤銷與接案資格仍在每次操作檢查。

作者只能回覆問題，須由有資格的驗題人確認結案。未結問題跨版延續並保留來源編號，不能用重新送審清掉。新增／重開問題或新的未確認回饋會撤下題面確認；結案後仍需明確留下新的確認回饋。審閱歷史保留操作者與時間，作者歷次回覆也記入工單事件紀錄。

審閱編號是此階段的題面版本，**不是完整 release revision**。目前尚未綁定不可變產物、部署 profile、PR revision 或個人同版試解證據；題面確認不會修改發布旗標或題目公開狀態。

## 多人同時工作

- 成員角色、工單和題目編輯都有版本檢查。舊表單送出會被拒絕；工單及題目編輯保留輸入，請比對最新資料後再送出。
- 同一筆題目的題敘、metadata、flag、tags、hints 在一次編輯中一起儲存或一起回復，不會只寫入一半。
- 送審、問題與回饋同樣檢查版本；過期回饋拒絕寫入並保留文字。題目與工單變更會使舊確認失效，不會套用到新版。
- 人員、截止或工時改變時重新要求接案；已確認的提案回到待確認。撤銷必要角色也會取消該成員的接案資格，重授角色不會自動恢復舊接案。
- 工單保留操作者、時間、接案／決策與變更紀錄。日期是送審日期，不是比賽截止事件；實際工時、驗題工時與跨工單個人負載彙總尚未接通。
- Git 協作仍沿用 repository 與 PR。插件 person_id／角色目前存於 staging DB；尚未同步至 `config.yml` 或 Git 身分映射，舊 setup 工具的 GitHub 欄位要求未改。

## 升級既有 staging

先保留 staging DB 備份。初始化新增協作表、題目編輯版本表與題面審閱表，保留原有題目及 ID，不會自動把既有使用者升為工作人員，也不會承認歷史「passed」為正式驗題。

啟用送審前，維運須配置獨立的 `IS1AB_REVIEW_FINGERPRINT_KEY`（至少 32 字元，建議用 `openssl rand -hex 32` 產生）。保存於部署用的私有環境設定，不提交 Git；所有 staging 副本使用同一值並跨重啟保留。不能重用 CTFd session secret 或產物簽署金鑰。沒有設定時仍可製作草稿，但送審會清楚提示設定未完成，且不留下半筆紀錄。輪換此值會使舊審閱失效，需重新送審。

兩份開發 Compose 設定已轉入此環境變數，並移除 Docker 主機 socket 掛載。VM 設定範例見 `ctfd-plugin/.env.dev-vm.example`。這些是部署檔修改，既有 staging 服務需另行更新才會生效。

若既有工單有重複 `challenge_id`，初始化會列出問題 ID 並停止，請人工確認正確對應再升級；不會猜測或覆寫。正常既有工單的作者／驗題人會成為待接案，提案狀態為草稿。

原生 `/challenges` 對已授權工作人員導向待辦；原生題目 API 和附件下載僅供管理員。這是此階段避免繞過題目權限的暫時限制，原生試玩／附件下載尚未提供給驗題人。舊私有資料如已被讀取、匯出或留在既有討論中，新增權限不會撤回已知資訊；升級時需檢查歷史分享內容及安排獨立驗題人。

舊版「自行加入驗題」「修改驗題名單」「標記通過」不可再用來改工單或產生通過紀錄；直接在 CTFd 執行 Docker 的三個入口回覆已停用。後續正式部署必須走獨立執行器與核准產物。

## 驗證方式與目前限制

既有測試：`uv run --extra dev pytest tests -q`。真實 CTFd 整合案例位於 `tests/integration/authoring_scenarios.py`，須在專案固定的 `ctfd/ctfd:3.7.5` 容器內執行，並把此 repository 唯讀掛載為 `/repo`、插件掛載至 CTFd 插件目錄。該容器另需 lockfile 版本 `PyYAML==6.0.3`。

```sh
PYTHONPATH=/opt/CTFd python /repo/tests/integration/authoring_scenarios.py
```

測試使用 CTFd TestingConfig 與獨立記憶體 SQLite，每個案例分開初始化；沒有使用 production 資料。`tests/integration/preview.py` 是受環境變數與臨時 DB 路徑限制的本機人工／瀏覽器 QA 輔助程式，不可作為部署入口。

尚未完成：同版本試解證據、產物簽署與核准、正式發布／回滾、production 的一人一隊強制規則與隊伍資源隔離、賽中案件及維運介面。MySQL/MariaDB 實際遷移與真正平行交易壓力尚未驗證；目前確認的是 SQLite、過期表單與資料庫唯一／版本限制。
